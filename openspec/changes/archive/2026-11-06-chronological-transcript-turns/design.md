## Context

Проверено в текущем checkout 2026-11-05:

- `PipelineRunner.assembleDocument` группирует слова отдельно по channel, затем сортирует уже готовые turns. Это объясняет возможность чужой реплики внутри длинного абзаца по времени.
- `PipelineLogic.groupTurns` и `groupTurnIndices` содержат порог 2,0 с. `mergeTwoChannels` умеет учитывать внешние границы, но сборка JSON его не вызывает. Проверка одного helper не доказывает поведение producer.
- `TranscriptReviewWindow` получает все `activeTurnIDs` из `TranscriptIntervalIndex`, подсвечивает каждый и передаёт список в `TranscriptFollowState`.
- Текст собирается независимо в App, `TranscriptExportFormatter` и `TranscriptPublisher`. Прямое дописывание `…` к word.text повредит исходное распознавание и смешает оформление с правками.
- По скриншотам неизвестны версия установленного приложения, конкретный result и точные интервалы слов. Провал амплитуды общего микса не доказывает отсутствие речи отдельного источника. Эта проверка остаётся первым пунктом реализации.

Перед реализацией прочитаны ADR-0001…0007. ADR-0004 заменяет только положения ADR-0001/0003 об истории/выборе результата; ADR-0005 заменяет только flat-retry положение ADR-0004. ADR-0006/0007 закрепляют workspace и модальные настройки; их компоновка сохраняется. Остальные положения остаются в силе.

## Goals / Non-Goals

**Goals:** порядок чтения A → вставка B → продолжение A; разбиение по паузе от 1,5 с; парные троеточия как оформление; максимум одна подсветка и тот же адресат автоскролла; сохранить редактирование и экспорт.

**Non-Goals:** смена ASR/диаризации, изменение аудиомикса, новые настройки, распознавание смысла пауз, миграция старых результатов, автоматический перенос правок, новый экран или дизайн плеера.

## Decisions

### 1. 1,5 с как исходный продуктовый порог

Это эвристика читабельности. В исследовании четырёх чешских диалогов медианы тихих пауз составляли 274–401 мс, дыхательных — 425–572 мс ([Weingartová et al., 2014](https://www.isca-archive.org/speechprosody_2014/weingartova14b_speechprosody.pdf)). Это небольшой корпус другого языка, а не универсальная норма. Исследование 15 часов спонтанной русской речи у 60 участников показывает сильные различия длительности пауз между людьми ([Kachkovskaia & Skrelin, 2020](https://www.isca-archive.org/speechprosody_2020/kachkovskaia20_speechprosody.pdf)). Ни одна из работ не устанавливает 1,5 с как границу мысли.

Предлагается снизить 2,0 → 1,5 с без пользовательской настройки. Проверить на двух сообщённых примерах и одном непрерывном монологе, не дробится ли речь чрезмерно. Порог считается по word timestamps. Если они не отражают слышимую длинную паузу, сначала документировать конкретное расхождение; изменение выравнивания/VAD требует отдельного уточнения этого плана, а не скрытого второго алгоритма.

### 2. Общий порядок слов

Сначала объединить `docWords` с сохранёнными `speakerID`/source ownership, отсортировать по start, source (host перед remote), ordinal в источнике. Затем группировать последовательные слова одного speakerID с паузой 1,5 с и существующими ограничениями длины/пунктуации. Внутри слова разреза нет: слово, начавшееся до вставки, целиком остаётся перед ней, даже если его end позже.

При продолжительном наложении фрагменты могут стать короткими вплоть до одного слова. Это принятое следствие буквального порядка вставок; не добавлять минимальную длину, которая снова спрячет вставку в длинном абзаце. Детерминированный порядок равных start обязателен.

`turn.start = min(word.start)`, `turn.end = max(word.end)`; реальные пересечения сохраняются. Запрещено укорачивать turn.end до следующего start для устранения двойной подсветки: это нарушает охват слов. Исправление проверить на публичной границе сборки документа и publisher, а не только на helper.

### 3. Троеточия — общее оформление в Core

Переиспользовать один небольшой чистый расчёт правил границ/продолжений для producer и представления. Поместить общие правила в Core: App не должен зависеть от Pipeline. Конкретный интерфейс выбрать при реализации по существующим типам, без универсальной системы форматирования.

Для определения продолжения восстановить базовые абзацы каждого speakerID из его исходных words по тем же правилам pause/duration/punctuation, временно исключив чужие слова. Когда один такой абзац представлен несколькими реальными turns, разделёнными чужими turns, это кандидаты на парные маркеры. Добавлять пару только между соседними фрагментами этого абзаца и при отсутствии конечной пунктуации перед разрезом. Каждый из двух turns должен быть точным непрерывным срезом одного базового абзаца, с соседними границами слов; все промежуточные turns принадлежат другим speakerID. Проверка локальная: поздний turn, пересекающий лимит 30 с базового абзаца, не запрещает раннюю однозначную пару. Это работает и для нескольких голосов на одной дорожке. Не пересобирать сохранённые turns ради показа маркеров. Для старых нестандартных границ без однозначного соответствия маркеры не добавлять.

В итоговом чтении: `текст…`, вставка, `…продолжение`. Оригинальные слова/пунктуация остаются побайтово прежними. Не дублировать уже имеющиеся `…`/`...`; если исходная граница уже завершает предложение, пару не создавать. Пауза сама по себе не получает маркеров.

App хранит отдельно текст для чтения и текст для редактирования либо вызывает форматирование только в чтении: `beginTextEditing` не должен сохранять автоматически показанные маркеры. Ручной text override авторитетен и выводится точно как сохранён, без автоматического оформления этого фрагмента; соседний неизменённый фрагмент может сохранить свой маркер. Копирование видимого текста получает его видимое оформление. Пользовательский экспорт и generated TXT используют тот же расчёт, сохраняя свои существующие заголовки/allowlists.

Альтернатива — новые поля JSON с причинами разрыва — сейчас не нужна: причину можно вычислить из исходных слов, существующих turns и одного набора правил. Не добавлять фиктивные слова `…` и не менять baselineWords.

### 4. Фокус чтения отдельно от физических интервалов

Сохранить существующие методы interval index для всех реальных пересечений. Рядом добавить вычисление одного фокуса чтения: последняя начавшаяся ненулевая реплика, при одинаковом start последняя по display order; подсветить её только пока position < end. Это эквивалентно обрезанию только окна подсветки следующим start, без изменения document.

Не возвращать фокус к старому длинному абзацу после окончания вставки: при движении вперёд фокус не прыгает назад. В паузе допустимо отсутствие подсветки. Нулевые интервалы не перехватывают фокус. Seek вычисляет его заново без зависимости от предыдущего tick.

В `TranscriptReviewWindow` передавать `[]` или `[focusID]` в существующие подсветку и follow. Логику `TranscriptFollowState` менять только при доказанной необходимости: её интерфейс уже допускает такой список. Компоновка строки, кнопки, таймкоды и транспорт остаются прежними.

### 5. Области и границы проверки

| Область | Работа | Проверка |
|---|---|---|
| `PipelineLogic.swift`, `PipelineRunner.swift` | merge до grouping, 1,5 с, единые правила | `PipelineLogicTests`, `PipelineDocumentAssemblyTests`: точная последовательность wordIDs, все слова ровно один раз |
| Core, `TranscriptExport.swift` | общие маркеры и точный override | formatter tests, сохранность words/baselineWords и edits |

## Risks / Trade-offs

- [Неверные word timestamps скрывают тишину] → сравнить исходные метки и соответствующий звук; не объявлять исправление пауз завершённым по synthetic fixtures.
- [Скриншот от другой версии] → зафиксировать установленную версию и producer result перед выводом о конкретной записи.
- [Перекрытия дробят речь] → явная приёмка примера с длинным overlap; сохранить каждое слово, не объединять обратно через чужую вставку.
- [Троеточие выглядит как распознанная пунктуация] → хранить его только в представлении, raw editing и manual overrides проверять отдельно.
- [Один фокус не отражает все одновременно звучащие голоса] → это намеренный выбор места чтения; аудио и timestamps остаются точными.
- [Расхождение трёх formatter paths] → общий Core-расчёт, одинаковые fixtures для App/export/publisher.
- [Существующие длинные абзацы остаются длинными] → разбиение меняется только в новом результате, старые правки не теряются при открытии.

## Migration Plan

Миграция файлов и JSON не нужна. Новое разбиение — только в новых результатах. Старые документы используют новую политику единственного фокуса, но сохраняют существующие turns/edits. Повторная обработка проходит существующий явный retry и атомарную публикацию; прошлые файлы сохраняются без переноса правок. Ошибка оставляет прежний результат доступным.

При откате приложения файлы совместимы с JSON v1; новый порядок turns остаётся валидным. Публикация и установка не входят в этот план. При синхронизации OpenSpec согласовать правила с ещё активными `swift-mlx-pipeline` и `transcript-editor`; старые 2 с и multi-highlight не должны остаться параллельными нормативными требованиями.
