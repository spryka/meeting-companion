# Участие в разработке

Meeting Companion использует OpenSpec со схемой `intent-driven` для изменений поведения и TDD для проверяемой логики. Автор PR отвечает за результат независимо от использования AI.

## Подготовка

Сборка описана в [README](README.md), ограничения и команды проверок в [AGENTS.md](AGENTS.md).
Установите OpenSpec CLI (`brew install openspec` на macOS), выполните `openspec init` в репозитории и выберите своего агента. Версия текущей настройки: 1.15.0. OpenSpec не входит в зависимости приложения.

## Рабочий цикл

1. Прочитайте действующие решения в `adr/`, относящиеся к задаче `openspec/specs/` и активные `openspec/changes/`. Предложение не означает, что функция уже реализована.
2. Для изменения поведения, контрактов или формата данных подготовьте OpenSpec change: проблему, требования, сценарии GIVEN/WHEN/THEN, дизайн, проверку ADR и задачи. Согласуйте их до реализации. Для контрибьютора подходит draft PR с документами.
3. Реализуйте небольшими проверяемыми частями. При изменении согласованного поведения обновите спецификацию.
4. Выполните `openspec validate <name> --strict`, тесты и необходимые ручные проверки. Валидация документов не доказывает выполнение требований.
5. После ревью и приёмки архивируйте change через OpenSpec с синхронизацией основных спецификаций. Не архивируйте непроверенную реализацию.

В `spec.md` храните проверяемые требования, в `design.md` или `context.md` причины решений и примеры. Документируйте существующий код по мере изменения. Простые правки текста и рефакторинг без изменения поведения не требуют новой спецификации.

## Архитектурные решения

Схема хранится в `openspec/schemas/intent-driven/` вместе с лицензией и версией
источника. После клонирования отдельно скачивать её не нужно. Проверка настройки:
`openspec schema validate intent-driven`.

Порядок документов: proposal → specs и design → adr → tasks. Для каждого change
создаётся `adr.md` с результатом проверки действующих решений. Если нового
долгосрочного решения нет, достаточно явно указать это в отчёте.

Решения, влияющие на следующие изменения, хранятся в корневом `adr/`: контекст,
выбранный подход и последствия. Агент предлагает решение; статус `accepted`
требует согласования сопровождающего и не означает готовность реализации.
Принятые ADR не переписываются. Новое решение заменяет старое через `Supersedes`.
Детали конкретной реализации остаются в `design.md`.

Дополнительные skills из upstream `skills.txt` не установлены. Сценарии Markdown
не исполняются автоматически; проверки пишутся средствами проекта.

## TDD

- Для бага сначала напишите регрессионный тест на наблюдаемый сбой.
- Для новой логики, форматов данных, очереди и сохранения: падающий тест по сценарию, минимальная реализация, рефакторинг при зелёных тестах.
- Подтвердите падение по ожидаемой причине. Ошибка импорта или окружения не считается воспроизведением. Для проверки прежнего поведения используйте временную копию или worktree, не откатывайте чужие правки.
- Проверяйте поведение через подходящую публичную границу. Не закрепляйте приватные методы и внутренний порядок вызовов без необходимости.
- UI-логику проверяйте автоматически, внешний вид и взаимодействие вручную. Аудиоустройства, разрешения macOS, качество звука и длинные записи требуют UAT на реальном Mac.
- Простые текстовые и визуальные изменения не требуют TDD. Исследовательский прототип может обходиться без него, но перед включением в продукт получает контракт и проверки.
- Если падающий тест практически невозможен, объясните причину и альтернативную проверку в PR. Фиктивные тесты не нужны.

## Ревью и завершение

Один PR решает одну связную задачу. Укажите спецификацию (или причину её отсутствия), команды и результаты проверок, непроверенные сценарии. Агентское ревью дополняет ревью сопровождающего. Галочка в tasks.md означает проверенное выполнение. Не ослабляйте тесты ради зелёного результата.

Записи, личные транскрипты, календарные данные, ключи и машинные пути в репозиторий не добавляются. Тестовые данные должны быть синтетическими. Пользовательские изменения записывайте в CHANGELOG.md под `[Unreleased]`. Публикация и установка выполняются отдельно от приёмки PR.
