# ADR-0011: Отбор чистых подокон и групповое автоназначение по метке Speaker N

Status: proposed
Date: 2026-11-21
Supersedes: ADR-0008 — только пункты §4 (отбор при отсутствии `voice-quality.v1.json` и независимый от порядка начальный отбор профиля), §6.5–6.6 (отбор чистых подокон 3–6 с и групповое автоназначение по метке `Speaker N` с защитой от смешанных кластеров), §7 (явный этап определения голосов перед завершением обработки и локальное включение политики по решению владельца) и соответствующие критерии Validation.

## Context

Экспериментальная проверка политики [ADR-0008](0008-local-voice-identity-profiles.md) на десяти реальных встречах (3386 реплик) выявила критически низкое покрытие поодиночного сопоставления целых реплик (на контрольной встрече из 412 реплик до сравнения дошли 4 и были подписаны 2 — 0.5%):

1. Около половины реплик короче 3 секунд и не могут быть оценены изолированно.
2. Почти половина длинных реплик имеют внутренние паузы, дыхание или краевые пересечения `overlap`/`otherTurns`, из-за чего требование непрерывного покрытия всей реплики `[turn.start, turn.end]` целиком отбрасывает годные 3–6-секундные фрагменты.
3. В большинстве уже сохранённых записей отсутствует `voice-quality.v1.json`, поэтому без опоры на интервалы слов `document.words` не удаётся отделить речь от внутренних пауз без повторного запуска диаризации.
4. Жадное последовательное добавление эталонов при первичной сборке профиля зависит от порядка кандидатов: один шумный фрагмент в начале списка способен заблокировать сборку рабочего профиля.
5. Условие присутствия совпавших окон в двух третях общего интервала присутствия `Speaker N` на встрече отбраковывало единогласные группы докладчиков, выступающих одним связным блоком, при том что остальные их реплики — короткие приветствия `< 3` с.

На тех же 10 встречах отбор чистых подокон 3–6 с и групповое сопоставление по кластерам `Speaker N` с защитой от смешанных групп обеспечили существенный рост покрытия (включая до 100% на чистой контрольной встрече) при 0 ошибок на размеченных репликах и 0 ложных срабатываний на незнакомых голосах.

## Decision

### 1. Отбор чистых подокон для сопоставления (`.matching`) и обучения (`.learning`)

1. Рассматриваются реплики длительностью `>= 3.0` с с отступом `0.15` с по краям: `trimmed = [turn.start + 0.15, turn.end - 0.15]`.
2. Источник интервалов речи:
   - при наличии `voice-quality.v1.json` с `evidence.speech != nil` для `.matching` используется `merged(evidence.speech, maxGap: 0.60)`, а для `.learning` — строгое `merged(evidence.speech)` (`maxGap = 0`); для `.matching`, если `evidence != nil` и `evidence.speech == nil`, возвращается `.refused(.missingEvidence)`;
   - при отсутствии `evidence?.speech` для `.matching` (только когда `evidence == nil` и подтверждена диаризация источника `source.diarizationStatus == .completed && (source.detectedVoiceCount ?? 0) > 0`) и для `.learning` (если `evidence?.speech == nil`) интервалы речи строятся по словам `document.words` с тем же `speakerID`, пересекающим реплику, с объединением соседних слов при зазоре `<= 0.60` с для `.matching` и `<= 0.40` с для `.learning`; при отсутствии подходящих слов (или неподтверждённой диаризации для `.matching`) возвращается `.refused(.missingEvidence)`. Для реплик из нескольких слов (`turnWords.count > 1`) аномально растянутые слова CTC (`duration > max(2.5, 1.2 * tokens)`) ограничиваются до `min(end, start + max(1.5, 0.8 * tokens))`, чтобы хвостовая тишина не считалась речью. Скрытый повторный запуск диаризации не выполняется.
3. Из пересечения `trimmed` и объединённой речи исключаются известные пересечения (`otherTurns` той же дорожки `sourceID` и `evidence?.overlap ?? []`), расширенные на `±0.10` с.
4. Для `.matching` оставшиеся чистые подотрезки переводятся во фреймы 16 кГц с округлением внутрь (`ceil(start * 16000) .. floor(end * 16000)`) с точной проверкой представимости `Int(exactly:)` (непредставимые границы дают отказ, без переполнения) и фильтруются по длине `>= 48_000` отсчётов (`3.0` с).
5. Для реплики в `.matching` по умолчанию (`extractMatchingSubwindows(..., maxWindows: 1)`) выбирается один самый длинный пригодный подотрезок (при равенстве — более ранний), и из его центра берётся одно окно длиной `min(length, 96_000)` отсчётов (`3.0..6.0` с). При строгой по-репликовой проверке внутри смешанного кластера (`extractMatchingSubwindows(..., maxWindows: 3)`) из пригодных подотрезков одной реплики извлекается до `3` непересекающихся окон 3–6 с (длинные чистые участки `> 6` с делятся на сбалансированные 3–6 с или центрированные 6 с фрагменты). При отсутствии пригодных подотрезков возвращается `.refused(exclusions.isEmpty ? .insufficientSpeech : .overlap)`.
6. При выборе окон на уровне группы (`VoiceAutomaticAssignment`) и при лимите 4 окон ручного обучения (`VoiceLearningCoordinator`) окна с плотной речью (`effectiveTokens >= windowDuration` с учётом доли пересечения слов) имеют приоритет перед разреженными/односложными окнами; при отсутствии плотных окон сохраняется прежний набор чистых окон без потери покрытия.

### 2. Независимый от порядка отбор начального профиля

1. При первичной сборке профиля (`compatibleActive.isEmpty`) входные кандидаты пакета приводятся к каноническому порядку (по ключу встречи, дорожке, интервалу, реплике, отпечатку PCM, назначению и идентификатору) **до дедупликации и балансировки**, а оценка клики и сборка активного профиля используют единый канонический порядок и общий расчёт длительности и достаточности по точным 16 кГц фреймам (`48_000...96_000` на окно, `>= 192_000` фреймов / `12` с суммарно — совпадает с проверкой при отзыве эталонов), чтобы перестановка входа не меняла ни итоговый центроид, ни состав 4 окон встречи. При обновлении резерва непопавшие новые кандидаты ставятся перед старыми отложенными образцами в пределах тех же лимитов (`<= 4` на встречу, `<= 12` всего), чтобы ранние несовместимые окна не блокировали последующее накопление.
2. Поиск максимального взаимно согласованного подмножества (максимальной клики в графе попарных `cosine >= minimumAgreement`) выполняется **точно** в поддерживаемом пределе кандидатов (`<= 24` элементов в `pending`); при превышении этого предела обновление явно отклоняется без частичного или приближённого результата.
3. При выборе оптимального подмножества приоритет задаётся детерминированно: достижение достаточности профиля (`>= 3` окна и `>= 12` с после балансировки по встречам), наибольший размер клики, наибольшее минимальное попарное сходство, наибольшая сумма попарных сходств, канонический порядок образцов.
4. Производственная политика ручного обучения обновляется до `manual-v1-agreement-0.60` (`minimumAgreement = 0.60`).

### 3. Ограниченный бюджет окон и групповое автоназначение по `Speaker N`

1. Учитываются только неподписанные реплики (`edits.overrides[turn.id]?.displayName == nil`) источников с подтверждённой диаризацией (`diarizationStatus == .completed && (detectedVoiceCount ?? 0) > 0`); группы неподтверждённой/сбойной диаризации получают `.missingEvidence` без группового переноса. Уже сохранённые ручные и машинные имена не перезаписываются.
2. По всем чистым кандидатам на каждой дорожке `sourceID` выполняется жадная дедупликация пересекающихся окон по возрастанию `(startFrame, turn.id)` (отброшенные пересечения фиксируются как `.overlap`). Длина окна в групповом сопоставлении проверяется по точным целочисленным фреймам 16 кГц (`48_000...96_000`), исключая погрешность `Double` на границе `6.0` с.
3. Общий бюджет первичного прохода на встречу ограничивается 1 батчем worker (`<= 64` окна, `VoiceEmbeddingProtocol.windowLimit`), и каждый отдельный запрос worker также ограничен `<= 64` окнами: в первичном проходе малые группы `Speaker N` получают все свои окна, большие делят остаток по watershed-квоте с выборкой ближайших уникальных окон к равномерно распределённым **временным точкам** (серединам окон). Реплики, не вошедшие только из-за квоты `<= 64`, не получают преждевременный отказ до группового решения.
4. Оценка каждой группы `Speaker N` выполняется по всем запланированным окнам этой группы, включая ответы worker с `embedding == nil` (тишина входит в знаменатель `windows.count`).
5. Для каждого окна фиксируется:
   - `strongLeader`: **акустический** лидер `top1` по косинусному сходству (`cosine >= policy.threshold`), независимо от календарного бонуса и `margin` (в том числе при победе другого профиля за счёт календаря);
   - `matchedPersonID`: победитель, прошедший все пороги (`threshold`, `margin`, ограниченный бонус подтверждённого контакта календаря и `maximumAcousticGap`). При расхождении между календарным победителем `matchedPersonID` и акустическим `strongLeader` в группе фиксируются оба лидера.
6. Группа `Speaker N` получает имя `P` (`origin = "automaticVoiceMatch"`), только если одновременно выполнены условия:
   - `strongLeaders == [P]` (ровно один сильный лидер во всех окнах группы, включая любого календарного победителя и всех акустических лидеров `>= threshold`);
   - при `windows.count >= 3`: `matchedCount(P) >= 3` и `3 * matchedCount(P) >= 2 * windows.count` (`>= 2/3` окон), без требования разброса по третям длительности группы;
   - при `windows.count in 1...2`: `matchedCount(P) == windows.count` (100% совпадений).
7. При выполнении правил имя `P` сохраняется для всех неподписанных реплик этой группы (включая короткие `< 3` с, реплики с паузами и реплики вне квоты батча).
8. При нарушении правил групповое автоназначение отменяется:
   - при признаках смешанной группы (`strongLeaders.count > 1`) и отсутствии `policy.mixedClusterRescue` всем неподписанным репликам группы ставится отказ `.ambiguous`;
   - при заданном `policy.mixedClusterRescue` (`VoiceMixedClusterRescuePolicy(threshold: 0.65, margin: 0.20)`, строго акустическом режиме с `calendarBonus = 0` и `maximumAcousticGap = 0`) групповое распространение остаётся заблокированным; каждая измеренная в первичном батче реплика смешанного кластера сначала сверяется по своим первичным окнам (без их повторного извлечения), и если первичные окна не провалили строгую проверку, дополнительно проверяются непересекающиеся чистые подокна 3–6 с (до `3` подокон на реплику через `VoiceWindowSelector.extractMatchingSubwindows`), отправляемые батчами по `<= 64` окна с проверкой отмены и поколений функции/библиотеки перед каждым батчем; реплика точечно получает `automaticVoiceMatch` только если и её первичные окна, и все дополнительные подокна единогласно прошли пороги `0.65 / 0.20` на одного и того же человека без `nil` и конфликтующих лидеров, тогда как неизмеренные (вне квоты `plan.queries` или без окон) и не прошедшие проверку реплики смешанной группы получают `.ambiguous`;
   - в остальных случаях репликам выставляются точные причины отказа по результату окна/отбора/группы.
9. Ограничение один-к-одному между группами `Speaker N` и дорожками не вводится; один человек может быть назначен разным группам независимо.

### 4. Явный этап определения голосов в маршруте обработки и включение политики

1. При включённом запоминании и наличии политики сопоставления на момент постановки задания в маршрут `ProcessingProgressSnapshot` после `.saving` добавляется финальная станция `.voices` (**«Определение голосов»**, модель `WeSpeaker`; длина маршрута `5..7` этапов). При выключенной функции или отсутствии политики маршрут сохраняет `4..6` этапов.
2. Автоматическое сопоставление (`VoiceLearningCoordinator.automaticallyAssign`) выполняется **внутри** `ProcessingService.startTranscription` в едином тяжёлом слоте сразу после публикации нового `resultID` и до перевода `entry.phase` в `.completed` / открытия транскрипта, используя общий `openWriter` при retry (чтобы не конфликтовать с открытым lock записи) и прямой вызов `voiceRunner.extractVoiceEmbeddings` без повторной постановки в очередь `ProcessingService`.
3. Сбой worker, отсутствие двух совместимых профилей, неподтверждённая библиотека, устаревание результата или выключение функции на этапе `.voices` не срывают и не отменяют уже сохранённый ASR: `.saving` остаётся завершённым, `.voices` фиксирует `.skipped` или `.failed` с причиной (при сбое — неблокирующее предупреждение без `isError`), а итоговый статус задания остаётся `.completed`.
4. Фоновое `.learning` после ручного редактирования имён в редакторе по-прежнему выполняется асинхронно через `ProcessingService` без изменения маршрута или статуса ASR-обработки.
5. По согласованию владельца в локальной композиции приложения (`RecorderAppDelegate`) включается политика сопоставления `VoiceMatchPolicy(threshold: 0.60, margin: 0.15, calendarBonus: 0, maximumAcousticGap: 0, mixedClusterRescue: VoiceMixedClusterRescuePolicy(threshold: 0.65, margin: 0.20))` (`defaultVoiceMatchPolicy`). Требования независимого blind test и разрешения лицензионных notices весов перед публичным распространением сборки сохраняются.

## Validation

- Сохраняются требования раздельного split по целым встречам для enrollment/calibration/blind test перед публичной поставкой; локальное включение `defaultVoiceMatchPolicy` в приложении утверждено владельцем (`V09`) на основе 19-встречного offline `voice-bench` LOMO-замера (`gap06_rescueStrict`: 507/525 на `CX(CC) grooming`, 92.5% на `vq=0`, `0/1123` ошибок на размеченных репликах и `0/1363` ложных срабатываний на удалённых дорожках гостей).
- Проверяются короткие реплики `< 3` с в составе группы `Speaker N`, объединение пауз `<= 0.60` с в `.matching` при сохранении строгого `.learning`, монолитные выступления в одной трети встречи, отказ/строгий per-turn rescue с консенсусом подокон при смешанной группе (`strongLeaders.count > 1`), учёт `embedding == nil` в знаменателе, лимит квоты `<= 64`, сохранение ручных имён, старые записи без `voice-quality.v1.json` через `document.words` fallback, порядок-независимая первичная сборка профиля при `minimumAgreement = 0.60`, а также удержание `.processing` на этапе `.voices` и безопасная деградация при ошибках/пропусках/retry write lock.

## ADR review

Дополняет и частично замещает [ADR-0008](0008-local-voice-identity-profiles.md) (§4, §6.5–6.6, §7) без изменения принятых [ADR-0008](0008-local-voice-identity-profiles.md) и [ADR-0009](0009-enrol-voices-through-name-edits.md). Ограничения [ADR-0001](0001-preserve-recognition-and-user-edits.md)–[ADR-0007](0007-workspace-settings-modal.md) и [ADR-0010](0010-confirm-existing-speaker-name.md) полностью сохраняются: `result.json` остаётся неизменным, ручные имена сохраняют приоритет, MLX остаётся в изолированном worker, а пропуск/сбой `.voices` никогда не блокирует доступ к опубликованному ASR.

## Alternatives

- Сохранить строгое поодиночное сопоставление реплик с покрытием 100%: отвергнуто, так как на реальных встречах оставляет без имени >99% реплик и бесполезно для коротких реплик.
- Требовать совпадения в 2 из 3 временных третей группы `Speaker N`: отвергнуто, так как ложно отбрасывает 100% единогласных докладчиков на стендапах с одним длинным выступлением и короткими репликами.
- Оставлять мягкие (`T=0.60 / D=0.15`) индивидуальные автоподписи при провале группы или при `strongLeaders.count > 1`: отвергнуто ради безопасности смешанных кластеров — допускается только строгий чисто акустический per-turn rescue (`0.65 / 0.20`) по консенсусу подокон при выключенном календарном бонусе.
- Увеличивать `maxGap` до `0.8–1.0` с и снимать фиксированный `0.15` с edge trim: отвергнуто по результатам `voice-bench` (краевое дыхание и склейка пауз `1.0` с ухудшили точность).
- Запускать `automaticallyAssign` скрыто в фоне уже после `.completed`: отвергнуто по обратной связи владельца — пользователь открывал «готовый» транскрипт до появления автоимён и вынужден был переоткрывать запись.

## Consequences

Автоматическое сопоставление работает на чистых 3–6-секундных фрагментах даже при наличии коротких пауз `<= 0.60` с, краевых пересечений и отсутствии `voice-quality.v1.json`, покрывая также короткие реплики внутри подтверждённой группы `Speaker N` и уверенные реплики внутри смешанных кластеров без ложного распространения на всю группу; пользователь видит шаг «Определение голосов» в маршруте и открывает транскрипт уже с применёнными автоименами. Защита `strongLeaders.count == 1`, строгий консенсус подокон при `mixedClusterRescue` и учёт пустых ответов в знаменателе блокируют путаницу и тишину. В приложении включена политика `T=0.60, D=0.15` с `mixedClusterRescue(T=0.65, D=0.20)` (`RecorderViewModel.defaultVoiceMatchPolicy`), тогда как формальный blind test и лицензионные notices весов остаются гейтом для публичного релиза по `V09`.
