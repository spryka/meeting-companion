# Пилот короткого цикла разработки

Цель: доводить небольшое изменение до проверенного результата с меньшим числом
передач между агентами и вмешательств владельца.

Сохранение пилота согласовано 2026-11-05. Первый запуск на реальной задаче
`chronological-transcript-turns` разобран 2026-11-06. Для этой задачи явно
согласованы ведущий writer без прораба и свежий reviewer после каждого связного
куска. Постоянный статус схемы и вариант с одним reviewer на всё изменение
не согласованы. Replay прошлых миграций не запускаем.
Документ не меняет активные треды, общие skills и требования
[AGENTS.md](../AGENTS.md), [CONTRIBUTING.md](../CONTRIBUTING.md) и принятых ADR.

## Предлагаемая схема

**Предварительно:** один ведущий агент обсуждает задачу, пишет код и отвечает за
результат. Второй агент независимо читает изменение и ищет ошибки. Постоянного
посредника, который только передаёт задания исполнителю, нет. Основание: в
разобранных сессиях цепочка координации разрослась. Пересмотреть, если ведущий
теряет требования или задача требует нескольких независимых исполнителей.

**Предварительно:** полное независимое ревью проводится для связного результата,
например исправления поведения капсулы вместе с её callers и тестами. Каждая
галочка tasks.md не требует отдельного полного ревью. Исправления возвращаются
тому же reviewer с новым diff. Основание: повторные проверки промежуточных
частей не предотвращали дефекты в приложении. Пересмотреть при пропусках ошибок
на границах модулей. Независимость reviewer и полнота доступа к коду сохраняются.

## Перед первой задачей

Выбрать одно небольшое наблюдаемое изменение. Объяснить владельцу схему выше и
согласовать её применение к этой задаче. Не перезапускать текущую инициативу.

Проверить checkout, Git status, действующие инструкции, затронутые specs/ADR и
доступность сборки и проверки результата. До UI-правок проверить, доступен ли
поддерживаемый запуск и осмотр приложения. При недоступности назвать точный
блокер. Не строить новый стенд и не менять разрешения автоматически.

В существующих документах задачи записать: что пользователь сможет сделать,
сценарии приёмки, что не входит в работу, ограничения и разрешённые действия.
Новый формат данных, архитектура и расширение scope требуют согласования.
Ненужные функции и исследовательские сравнения не добавлять в путь поставки.

## Рабочий цикл

1. **Воспроизвести.** Прочитать реальных callers. Для проверяемой логики получить
   ожидаемое падение регрессионного теста. Для чисто визуальной правки сохранить
   исходное изображение и условия воспроизведения, без фиктивного RED.
2. **Исправить и рано проверить в приложении.** Использовать существующие
   компоненты. Проверять именно заявленный сценарий: клики для hit area,
   изображение для отрисовки, реальный App/CLI маршрут для подключения сервиса.
   Геометрия, сборка и source review не доказывают видимый результат.
3. **Получить независимое ревью.** Передать требования, baseline/diff, полный
   релевантный код, callers и результаты проверок. Reviewer не пишет продуктовый
   код. По каждому замечанию принять решение с доказательством. Пожелания вне
   задачи не становятся обязательными исправлениями.
4. **Исправить замечания в пределах бюджета.** Сохранять существующие счётчики.
   Если отдельный бюджет не задан, максимум два раунда исправлений. Повтор того
   же дефекта требует проверки причины и способа наблюдения. Новое название
   пакета не обнуляет лимит. При исчерпании сообщить конкретный блокер и варианты.
5. **Проверить итог и передать результат.** Выполнить обязательные проверки
   проекта для итоговой ревизии. Повторять их после правок, которые могли
   обесценить результат. Установку проводить только в разрешённом scope и с
   соблюдением защиты активной записи и обработки. Непроверенное оставить открытым.

Команды финальной проверки определены в AGENTS.md: `swift build -c release`,
`swift test`, `bash scripts/check-module-boundaries.sh` и
`swift skills/local-audio-transcriber/scripts/find-recording.swift --self-test`.
Для change выполнить `openspec validate <name> --strict`, для упаковки использовать
`./scripts/build-app.sh`. Этот пилот не отменяет обязательные проверки.

Сохранность исходных записей, правок и транскриптов обязательна. Исследование
качества моделей и длительные аппаратные прогоны планируются отдельно. Короткий
smoke не доказывает качество на длинных встречах. Работа с аудио требует явно
заданного разрешённого объёма, а не самостоятельного расширения матрицы прогонов.

## Доказательства и передача

Переиспользовать документы задачи: контракт, baseline/diff, логи команд с exit
codes, замечания reviewer и короткое текущее состояние. Сохранять исходное dirty
состояние и необходимые снимки затронутых файлов. Не копировать весь репозиторий
и не создавать повторные отчёты без нового решения или результата. Если активный
skill требует более тяжёлого протокола, согласовать исключение до запуска, а не
молча игнорировать его.

Полный доступ reviewer к коду не требует вывода каждого файла целиком. Сначала
найти нужные определения и callers, затем прочитать полные связанные функции,
инварианты и тесты. Расширять чтение по найденным зависимостям. Для повторного
ревью начинать с изменений после предыдущей проверки и затронутых связей.
Сохранять полные логи, в контекст выводить итоги и относящиеся к замечанию ошибки.
Не заменять независимое чтение пересказом writer или произвольным лимитом строк.

В конце сообщить: что изменилось, как проверено, какая версия доступна и что
осталось непроверенным. Владельца спрашивать о продуктовых решениях, расширении
scope и реальных ограничениях доступа. Уже разрешённые действия не согласовывать
заново. Субъективную визуальную приёмку не заменять догадкой агента.

## Как оценивать следующие запуски

Записать время начала, первой рабочей версии и завершения. Отдельно учитывать
ожидание владельца и сбои инструментов. Посчитать повторные появления того же
дефекта, раунды исправлений и вынужденные вмешательства владельца. Обсуждение
продуктовых вариантов не считать лишним вмешательством.

После задачи проверить: сценарий действительно работает, записи сохранены,
обязательные проверки и независимое ревью завершены, результат был показан до
разрастания процесса. Один успешный пример не доказывает постоянное ускорение.
Общий skill обновлять только после разбора результата и отдельного решения.

Разделять время до первого частичного изображения, прохождения синтетических
сценариев, итогового изображения, ревью, установки и пользовательской приёмки.
Не называть первый GREEN готовым пользовательским результатом. Считать
вмешательства отдельно для реализации и установки, отмечать исключённую
подготовительную работу. Дополнительное разрешение после отказа инструмента
не считать ошибкой процесса, если оно требуется действующими правилами.

В BB счётчики можно брать из последнего `thread/tokenUsage/updated` в экспорте
точного треда. Брать одну итоговую запись на уникальную provider session, не
суммировать накопительные snapshots. Раздельно показывать input, cached input и
output. Reasoning не прибавлять второй раз к output. Если остался только один
snapshot, не выводить из него начальный контекст или стоимость отдельных этапов.
Денежная стоимость без тарифных данных неизвестна. Статическая оценка настроек
и символы сохранённого tool output не равны токенам запроса.

- Не считать визуальное исправление завершённым по source PASS.

  осмотра приложения обозначить как блокер визуальной проверки.
- Подтвердить результат новым изображением в тех же условиях либо оставить
  визуальную приёмку открытой. Не запускать бесконечные source-only раунды.
- Сохранить бюджет исправлений и границы задачи, не добавлять новый стенд или
  разрешения для обхода блокера.
